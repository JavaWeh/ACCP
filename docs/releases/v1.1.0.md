# v1.1.0

Feature release for the M7 / F3 wave: in-app notifications (F3), server-side audit
filters with redacted export (F4), a GitLab git provider (F6), and advisory task comments
with @mentions (F11). It builds on `v1.0.1` with three new migrations (`008`/`009`/`010`)
and a targeted grants change that operators **must** re-run after migrate. Prefer
digest-pinned images from the GitHub Release; do not install from a floating `latest` tag.

## Highlights

- **F3 — in-app notification center + unread badge** (US-20). A per-user projection of the
  project event feed: `emitEvent` writes each recipient's notification row in the **same
  transaction** as the business change, so the unread badge can never disagree with the
  facts it summarizes. Five types — `TASK_ASSIGNED`, `REVIEW_REQUIRED`, `APPROVAL_PENDING`,
  `TASK_BLOCKED`, `COMMENT_MENTION`. Read state is per-user and durable across refresh;
  retention is seven days, enforced at read time (no reaper). The bell sits next to the
  connection-status indicator and polls on the existing F1 cadence (no new WebSocket/push
  channel). Deep links focus the target: task → `/projects/:p/tasks/:id`, approval →
  `/projects/:p/approvals?approval=:id` (opens the approval Modal and scrolls the card,
  O-W11), mention → the task comment anchor.
- **F4 — server-side audit filters + redacted JSONL/CSV export** (US-21). Project and
  organization execution audit gain `actor` / `task` / `action` / `from` / `to` filters
  (cursor pagination preserved). New ADMIN-only project and org-ADMIN cross-project export
  endpoints stream JSONL/CSV through a fixed field whitelist that **never** serializes the
  raw `details` jsonb, so a future detail field cannot silently leak. Each export writes
  its own audit row (filter summary + row count + sha256 content hash). REVIEWER may list
  but not export (the console hides the button and the server returns 403). No new
  migration — filters and export are query-only.
- **F6 — GitLab git provider** (US-23). Register a GitLab repository (full HTTPS URL or a
  `group/project` short path), pull by pinned revision with the same `content_digest`
  algorithm as GitHub, and run a read-only "test pull" that returns a digest/revision or a
  classified `AUTH`/`NOT_FOUND`/`NETWORK` error and **never** echoes the token. Per-repo
  read-only credentials are stored encrypted at rest (AES-256-GCM via the existing
  `SessionSigner` with purpose `repo_access_token`), out of the repositories document jsonb
  so the generic document-returning handlers can never echo them. GitHub behavior is
  unchanged (still the server-level `ACCP_GITHUB_TOKEN`).
- **F11 — advisory task comments + @mentions** (US-24). Human-to-human discussion on a
  task that is **never** a state-transition channel: `task_comments` has no FK or trigger to
  task status/version, the `CreateComment`/`EditComment` schemas are
  `additionalProperties:false` with no status field, and comment handlers only ever write
  the comments table plus the F3 projection. @mentions of active members fan out a
  `COMMENT_MENTION` notification (invalid mention → 400, task untouched). Edits set an
  "edited" marker; deletes are soft (tombstone; no hard delete).
- **Web O-W11 deep-link focus** (`d04376e`) — the approval deep link now opens the target
  approval Modal and scrolls its card into view, flipping the filter to "all" if the
  approval is not pending; the `?approval=` query is cleared after use.

## Compatibility

Supported upgrade-from: `v1.0.1` (`docs/releases/v1.0.1.md`). Fresh install is also
supported.

- **Upgrade from `v1.0.1`**: apply the three new migrate files `008_notifications.sql`,
  `009_repository_tokens.sql`, and `010_task_comments.sql`, then **re-run grants** (see
  Migrations / Grants). Re-running grants is required this release — the F3 and F11 tables
  did not exist at `v1.0.1`, so a stale grant set leaves the `notifications` and
  `task_comments` tables without the INSERT/UPDATE the API needs.
- Installs older than `v1.0.1` should first reach `v1.0.1` (apply `006_task_query.sql` and
  `007_org_admin.sql` per those notes) and then apply `008`/`009`/`010`.

Untagged or pre-RC builds should treat this as a new install after backup, or follow the
documented adopt path separately.

## Migrations

Apply the normal production Compose sequence (`migrate` then `grants`) before returning
traffic. All three files are new on `main` relative to the `v1.0.1` tag.

1. **`008_notifications.sql`** (F3): creates the `notifications` table and its two indexes
   (newest-first keyset per recipient; partial index for the cheap unread-count summary).
   Notifications are a per-user projection of the event feed with a seven-day retention
   enforced at read time (`occurred_at`), so no separate reaper runs. The `type` column is
   constrained to `TASK_ASSIGNED` / `REVIEW_REQUIRED` / `APPROVAL_PENDING` / `TASK_BLOCKED`
   / `COMMENT_MENTION`. A foreign key to `memberships` ties each row to a real membership.
2. **`009_repository_tokens.sql`** (F6): adds `repositories.access_token text`. The value
   is authenticated AES-256-GCM ciphertext (SessionSigner purpose `repo_access_token`),
   stored **out** of the repositories document jsonb so the generic document-returning
   list/get handlers can never echo it. It is only read server-side when selecting a
   provider to verify or pull; it is never persisted in plaintext.
3. **`010_task_comments.sql`** (F11): creates the `task_comments` table (advisory only; no
   FK or trigger to task status/version) with `mentions text[] NOT NULL DEFAULT '{}'`,
   soft-delete (`deleted` tombstone with the body cleared) and an `edited` marker, plus a
   chronological (oldest-first) keyset index for one task's thread. Foreign keys tie each
   comment to its task and to a real membership.
4. No additional migrate files beyond current `main` are required for this tag once
   `008`/`009`/`010` and grants have succeeded. Production dumps carry the schema so a
   restore recreates these tables and indexes.

## Grants / privileges

Production installs must apply `deploy/production/grants.sql` after migrate, and this
release **requires** re-running it on upgrade: the new F3/F11 tables did not exist at
`v1.0.1`, so an un-refreshed grant set leaves them without the privileges the API needs
and both features break silently in production. This release adds these targeted grants to
`accp_api` beyond `v1.0.1`:

- **`notifications`** — `INSERT` (the same-transaction projection writes recipient rows)
  and `UPDATE` (mark-read sets `read_at`). No `DELETE` — notifications age out at read time
  via the seven-day retention window.
- **`task_comments`** — `INSERT` (create a comment) and `UPDATE` (author edit sets
  `edited`; author/ADMIN soft-delete clears the body and sets the tombstone). No `DELETE` —
  comments are soft-deleted, never hard-deleted.

`repositories` already carries `INSERT` for `accp_api`, which covers writing
`access_token` at register time; no new grant is required for F6. Least privilege is
preserved: runtime roles still receive `SELECT` on all tables, no `DELETE` on the two new
tables, and no `UPDATE` on `human_users.is_org_admin`.

`deploy/production/check-privileges.sql` now also asserts that `accp_api` **has** `INSERT`
and `UPDATE` on both `notifications` and `task_comments`, in addition to the existing
`v1.0.1` boundary checks (UPDATE on `human_users.active`, no UPDATE on
`human_users.is_org_admin`, etc.).

Verify with:

```sh
accp-ops check --database-url-file /run/secrets/migrator_url
```

On failure, re-run grants:

```sh
docker compose -f deploy/production/compose.yaml run --rm grants
```

Skipping grants on this upgrade silently breaks the F3 notification badge (no INSERT on
`notifications`) and F11 comment posting/editing (no INSERT/UPDATE on `task_comments`).

## Config / secrets / compose

1. **No new secret file names and no new env vars** for the F3, F4, or F11 features. GitHub
   still uses the server-level `ACCP_GITHUB_TOKEN`, unchanged.
2. **F6 GitLab credentials are per-repository, supplied at register time**, not via a
   server env var. They are encrypted at rest with the existing session-signing keys
   (SessionSigner purpose `repo_access_token`); no new signing-key secret is introduced.
   Editing a repository with a blank token leaves the stored credential unchanged, and no
   handler echoes it back.
3. Production still pins `ACCP_IMAGE` (and the ops image for backups) to Release digests;
   keep the SPA client ID (`ACCP_OIDC_CLIENT_ID`) distinct from the API audience
   (`ACCP_OIDC_AUDIENCE`).

## Breaking / operator actions

1. **Apply `008`/`009`/`010` and re-run grants before returning traffic.** Re-running
   grants is mandatory this release: the F3 `notifications` and F11 `task_comments` tables
   are new, so without a fresh grants run the API cannot insert notifications or write
   comments. Confirm with `accp-ops check`.
2. Pin `ACCP_IMAGE` (and the ops image for backups) to the digests published on this
   Release; do not use mutable local tags as the install identity.
3. After migrate, always run grants and confirm with `accp-ops check` before returning
   traffic.
4. Do not use `down -v` during upgrade or maintenance; named volumes hold PostgreSQL,
   JetStream, and Caddy state.
5. **Task comments are advisory only.** They never move a task, approval, Run, or owner;
   the API rejects any status/version field on a comment. Do not build process automation
   that expects a comment to drive state.
6. **GitLab access tokens are per-repository and read-only.** Provide a read-only token at
   register time; it is stored encrypted and never echoed. The read-only "test pull" never
   returns the token and does not auto-register the repository.

## Known limits

1. **F6 live GitLab pull not exercised this wave.** The GitLab provider ships with digest
   contract and error-classification unit tests (httptest), but a real GitLab fixture-repo
   trial pull with a live read-only token was **not** run — it needs an operator-provided
   test repo and token. Treat live GitLab acceptance as pending until that credential is
   available.
2. **Live GitHub fixture sync** remains an environment/token-hygiene issue
   (`TestGitHubLiveTokenSyncFixture` fails when `ACCP_GITHUB_TOKEN` is set but the live
   fixture is unavailable). This is not a code defect introduced by this wave — the GitHub
   fetch path is unchanged; the F6 change only adds an additive probe path.
3. Control-plane integration tests (`//go:build integration`) and full-DOM e2e require
   Docker/Postgres and a managed server; pure unit tests plus static review cover the
   digest contract, redaction, comment status-invariance, and mention projection in their
   absence.

## Known follow-up / P1

1. **Live GitLab acceptance** (F6): run the pinned-revision pull + digest check against a
   dedicated private test repo with a read-only token once credentials are available.
2. **Audit export ceiling**: export is capped at 50000 rows (413 over the ceiling); there
   is no byte cap or streaming yet. Revisit if journals grow.
3. **Full-DOM comment/notification e2e** (draft retained after a failed send, "@" opens the
   picker, auto-scroll, REVIEWER no-export button, blob download) remains managed-server
   e2e, deferred behind the pure-unit coverage.
