# v1.2.0

Feature release for the M8 wave: outbound signed webhook notifications (F5 / US-22),
saved task views with bulk actions (F7), and a per-run tool-invocation timeline (F8). It
builds on `v1.1.0` with one new migration (`011_webhooks.sql`), a targeted grants change
that operators **must** re-run after migrate, and one new operator environment variable
(`ACCP_WEBHOOK_ALLOWLIST`). Prefer digest-pinned images from the GitHub Release; do not
install from a floating `latest` tag.

## Highlights

- **F5 — outbound signed webhook notifications** (US-22). Project ADMINs register HTTPS
  endpoints that receive a redacted projection of the project event feed. Each endpoint
  subscribes to one or more of `REVIEW_REQUIRED`, `APPROVAL_DECIDED`, and `TASK_BLOCKED`
  (the last maps internally to the `TASK_FAILED` event kind, matching the F3 notification
  taxonomy). Delivery is defence-in-depth against SSRF: a destination must be HTTPS, on the
  operator-configured allowlist, and resolve only to public addresses — enforced both when
  the URL is configured and again at dial time (a `net.Dialer.Control` hook re-checks the
  actual connect IP, closing the DNS-rebinding window), with redirects refused. Each
  delivery carries an HMAC-SHA256 signature over `<timestamp>.<body>`
  (`X-ACCP-Signature: sha256=…`, plus `X-ACCP-Event`/`X-ACCP-Delivery`/`X-ACCP-Timestamp`).
  The per-endpoint signing secret is generated server-side, stored as authenticated
  AES-256-GCM ciphertext (SessionSigner purpose `webhook_signing_secret`), and echoed in
  cleartext exactly once (on create and on rotate) — never by list/get. Payloads are a
  field **whitelist** projection of the CloudEvents envelope, so no token or private
  Context body can leak, now or when a future event grows a field. Fan-out reads the
  existing deduplicated `event_feed` (so `internal/eventbus` is untouched) and deliveries
  reuse the `outbox_events` backoff shape; a new endpoint only ever receives future events
  (no historical backfill), and a delivery is abandoned after ten failed attempts rather
  than retrying forever.
- **F7 — saved task views + bulk actions** (`b0e6511`). Query-only; no migration.
- **F8 — per-run tool-invocation timeline** (`a9ea56a`). Query-only; no migration.

## Compatibility

Supported upgrade-from: `v1.1.0` (`docs/releases/v1.1.0.md`). Fresh install is also
supported.

- **Upgrade from `v1.1.0`**: apply the new migrate file `011_webhooks.sql`, then **re-run
  grants** (see Migrations / Grants). Re-running grants is required this release — the F5
  `webhook_endpoints` and `webhook_deliveries` tables did not exist at `v1.1.0`, so a stale
  grant set leaves the API unable to register endpoints and the worker unable to enqueue or
  record deliveries, and the feature breaks silently.
- Installs older than `v1.1.0` should first reach `v1.1.0` (apply `008`/`009`/`010` per
  those notes) and then apply `011`.

Untagged or pre-RC builds should treat this as a new install after backup, or follow the
documented adopt path separately.

## Migrations

Apply the normal production Compose sequence (`migrate` then `grants`) before returning
traffic. The one file is new on `main` relative to the `v1.1.0` tag.

1. **`011_webhooks.sql`** (F5): creates `webhook_endpoints` (one row per registered signed
   endpoint, carrying the AES-256-GCM-sealed signing secret, the subscribed event-type
   array, an `enabled` flag, a `version`, and a `delivered_sequence` fan-out high-water
   mark) and `webhook_deliveries` (one row per `(endpoint, event)` delivery intent,
   mirroring the `outbox_events` backoff columns — `attempts`, `next_attempt_at`,
   `last_status`, `last_error_code`, plus `abandoned_at` for the retry ceiling — with a
   redacted `payload` jsonb and a `UNIQUE(endpoint_id, event_id)` fan-out guard). A partial
   index serves the due-delivery scan; a foreign key with `ON DELETE CASCADE` ties
   deliveries to their endpoint. The signing secret is stored out of any document, so the
   generic document-returning handlers can never echo it.
2. No additional migrate files beyond current `main` are required for this tag once `011`
   and grants have succeeded. Production dumps carry the schema so a restore recreates
   these tables and indexes.

## Grants / privileges

Production installs must apply `deploy/production/grants.sql` after migrate, and this
release **requires** re-running it on upgrade: the new F5 tables did not exist at `v1.1.0`,
so an un-refreshed grant set leaves them without the privileges the API and worker need and
the feature breaks silently in production. This release adds these targeted grants beyond
`v1.1.0`:

- **`accp_api`** — `INSERT`, `UPDATE` and `DELETE` on `webhook_endpoints` (create / change
  subscription / rotate secret / enable / disable / delete; deleting an endpoint cascades
  to `webhook_deliveries` through the foreign key, which needs no child `DELETE` grant).
- **`accp_worker`** — `UPDATE` on `webhook_endpoints` (advance the `delivered_sequence`
  fan-out high-water mark) and `INSERT` + `UPDATE` on `webhook_deliveries` (enqueue a
  delivery intent and record success or a backed-off retry).

Least privilege is preserved: runtime roles still receive `SELECT` on all tables, the API
gets no access to `webhook_deliveries` beyond the shared `SELECT`, and no role is granted
`DELETE` on `webhook_deliveries`.

Verify with:

```sh
accp-ops check --database-url-file /run/secrets/migrator_url
```

On failure, re-run grants:

```sh
docker compose -f deploy/production/compose.yaml run --rm grants
```

Skipping grants on this upgrade silently breaks webhook registration (no `INSERT` on
`webhook_endpoints`) and all delivery (no `INSERT`/`UPDATE` on `webhook_deliveries`).

## Config / secrets / compose

1. **New operator environment variable `ACCP_WEBHOOK_ALLOWLIST`** (F5): a comma-separated
   list of host suffixes an outbound webhook URL may target (for example
   `hooks.slack.example.com,webhook.partner.example`). It is read by **both** the API
   (to validate a URL at registration time) and the worker (to re-validate at delivery
   time), so set it identically for both processes. An **empty or unset** allowlist is the
   safe default: every URL is rejected and outbound delivery is effectively disabled until
   an operator opts hosts in. Only public hosts can ever be used — loopback, RFC1918 /
   unique-local private, link-local (including the `169.254.169.254` metadata address), and
   other reserved ranges are refused regardless of the allowlist.
2. **No new secret file names.** Webhook signing secrets are generated server-side and
   encrypted at rest with the existing session-signing keys (SessionSigner purpose
   `webhook_signing_secret`); no new signing-key secret is introduced. GitHub still uses
   the server-level `ACCP_GITHUB_TOKEN`, unchanged.
3. Production still pins `ACCP_IMAGE` (and the ops image for backups) to Release digests;
   keep the SPA client ID (`ACCP_OIDC_CLIENT_ID`) distinct from the API audience
   (`ACCP_OIDC_AUDIENCE`).

## Breaking / operator actions

1. **Apply `011` and re-run grants before returning traffic.** Re-running grants is
   mandatory this release: the F5 `webhook_endpoints` and `webhook_deliveries` tables are
   new, so without a fresh grants run the API cannot register endpoints and the worker
   cannot deliver. Confirm with `accp-ops check`.
2. **Set `ACCP_WEBHOOK_ALLOWLIST` on both API and worker** if you intend to use outbound
   webhooks. Until it is set, every webhook URL is rejected by design. Add only the public
   receiver hosts you trust; internal and metadata addresses are always refused.
3. Pin `ACCP_IMAGE` (and the ops image for backups) to the digests published on this
   Release; do not use mutable local tags as the install identity.
4. After migrate, always run grants and confirm with `accp-ops check` before returning
   traffic.
5. Do not use `down -v` during upgrade or maintenance; named volumes hold PostgreSQL,
   JetStream, and Caddy state.
6. **Webhook payloads are a redacted projection and signed, not a control channel.** They
   carry ids, digests, decisions and status summaries only; receivers must verify the HMAC
   signature (and may check `X-ACCP-Timestamp` for freshness) before acting, and must not
   expect a token or Context body in the body.

## Known limits

1. **Live webhook delivery**: closed on 2026-11-03 against an allowlisted public receiver
   (HMAC + redaction PASS). Compose injects `ACCP_WEBHOOK_ALLOWLIST` (`f176616`). Keep the
   allowlist empty in production until you intentionally enable outbound webhooks.
2. **Full-DOM comment/notification/audit e2e** still has no managed-server Playwright
   coverage for draft/@/scroll, REVIEWER no-export toolbar, or blob download — unit helpers
   only. Recorded as open risk (not PASS).
3. **WP-5 50-distinct-user load** (2026-11-04): three runs at c=50 / 200 agents all **FAIL**
   Event visibility P95 (≈2.1–2.5 s vs 2.0 s SLO). Read/write/5xx met. See
   `docs/loadtest/w0-2026-11-04-50users.md`.
4. **WP-8 Windows Playwright**: case-insensitive clash between `SavedViews.tsx` and
   `savedViews.ts` broke UI specs on Windows; fixed by renaming helpers to
   `savedViewModel.ts` (local commit pending push). Re-verify exit 0 after that fix.
5. Control-plane `-tags=integration` suites require Docker/Postgres/NATS on the host
   network; they are green on the shared box when those services are up.
