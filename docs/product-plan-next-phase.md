## 1. 背景

【事实】ACCP（Agent Collaboration Control Plane）是一个自托管控制面，让人类团队和多种 AI 编码 Agent 在「人负责验收」的前提下协作完成任务。它不提供模型推理，也不把聊天记录当作编排数据库（docs/architecture.md）。技术栈：后端 Go + PostgreSQL 17 + NATS JetStream + OIDC + MCP，前端 React 19 + Vite。

【事实】PR #21 已合并 D07（任务编辑、交接、归档）和 D09（固定到 GitHub commit 的文本上下文同步及 diff 评审）。GitHub 上目前没有打开的 issue 和 PR，next-phase-plan.md 是 D07/D09 之后第一份结构化待办。

【事实】交付计划里仍未关闭的 P0 缺口：D06（容量验证）和 D10（版本化发布物）。D09 实现方自己标为「不计为通过」的两项验证也还没做：一是完整的 `go test -race -tags=integration` 因本地 Docker 断连而中断；二是 GitHub 同步只在匿名状态下测过，被 403 限流。

## 2. 问题陈述

1. **不能发布**：CI 每次都会构建镜像和二进制，但没有打 tag 和发布的流程，也没有升级说明（.github/workflows/control-plane.yml:55-63）。运维方拿不到「可安装、可支持」的版本。验证方式：仓库里不存在任何版本 tag 或已发布的制品。
2. **容量未知**：连接池硬编码为 `MaxConns = 10`（internal/database/database.go:25），事件投递由一把全局 advisory lock 串行化（internal/eventbus/worker.go:101）。没有压测结论，也没有冻结的目标规模（W0），因此无法回答「这套系统能支撑多少人和 Agent」。
3. **已合并功能的验证欠账**：D09 在真实 token 下的行为没有测过；从旧版升级的环境如果没有重新执行 `grants.sql`，D07 的「编辑任务后重新选择上下文」会静默失败（docs/d07-d09.md:25）。
4. **日常使用和可维护性**：控制台全量轮询（每 10 秒）；任务列表接口虽是游标分页，但排序写死为 `ORDER BY id`（task_query.go:72），不支持按其他字段排序，也不返回总条数；深链接已有基础能力，但登录跳转只保留路径（见 US-12）；三个前端大文件合计约 3,650 行（workspace.tsx 1527、main.tsx 1087、tasks.tsx 1042），后续改动成本会越来越高。已初始化的实例无法在界面上增删成员、项目或仓库（D01）。

### 2.1 与本期相关的现状【事实】（审计后经代码核对）

- **列表分页**：`listTasks` 只返回 `{items, next_cursor}`，没有总条数，也没有 `COUNT(*)`（task_query.go:93）。游标是绑定 `id` 和筛选条件的 keyset 游标（task_query.go:38-47、93-98），排序写死为 `ORDER BY id`（:72），没有 sort 参数。注意：id 是随机生成的 16 字节十六进制串（server.go:377 `newID`），**与创建时间无关**，所以现在的默认顺序没有业务含义，既不是创建顺序，也不是最新在前（O3a）。
- **权限语义**：非项目成员（或项目不存在）访问项目资源时返回 **404** `NOT_FOUND`「Project not found」；是项目成员但角色不够时返回 **403** `FORBIDDEN`（server.go:240-254）。
- **成员停用**：目前只有**项目级**停用，即 `UPDATE memberships SET ... active`（identity.go:90），停用时只吊销该用户**在本项目委托的 Agent/MCP 会话**（`revokeManagedSessions`，management.go:287-288：`agent_sessions` 中 `project_id` 为本项目且 `delegated_by_user_id` 为该用户的记录）；**不影响其本人的 OIDC 登录，也不影响其他项目**（O12）；不允许停用项目里最后一个 ADMIN（409 `LAST_ADMIN`）。没有任何写路径会设置 `human_users.active`，该字段只被读取（sessions.go:59、72），因此**不存在账号级停用**。停用成员不会处理其名下的任务。
- **幂等重放**：命中 `idempotency_records` 时原样返回缓存的 status、body 和 etag（server.go:285-300）；`respond()` 只设置 `Content-Type` 和 `ETag`（:355-361）。前端**无法区分**「首次成功」和「重放结果」。
- **深链接**：路由已支持 `/projects/{id}/{page}` 和任务详情（routing.ts）。OIDC 登录前把 `location.pathname` 存入 `returnTo`（main.tsx:511），回调时校验它是同源相对路径后恢复（main.tsx:220-237）；开发模式下有对应的 `returnTo` 查询参数（main.tsx:471-478、500）。**缺陷**：只存了 pathname，**查询参数和 hash 会丢**。路由里无法识别的 page 段会静默回退到 overview（routing.ts:32）。
- **项目归档**：已有 `ARCHIVE` 和 `RESTORE` 两个命令（management.schema.json；management.go:184 起）。项目里还有未完成的任务、运行中的 run 或待处理的工具调用时，**拒绝归档**。

## 14. UI 需求

需要 UI 设计师 **jack** 设计的界面如下。其余故事（W0、压测、验证欠账、授权检查、发布流水线、前端拆分、文档、US-11a 和 US-13a 两个后端子任务）**不需要 UI 设计**。前端拆分（US-10）要求视觉零变化。

1. **任务列表的筛选、排序和逐页加载（US-11b）**：筛选栏（状态、负责人；**本期不加「项目」筛选**，见 O2）；排序控件只提供「更新时间」和「标题」，支持升序和降序，**界面上要始终有一个明确的排序选项被选中**（默认选「更新时间 降序」，由前端显式传 sort 给后端；不能依赖后端默认顺序，也不能把它标成「创建顺序」或「最新」）；**分页器改为「加载更多」按钮或「下一页」**，后端不返回总数，所以**不显示总条数、页码或「本页 N 条 / 共 M 条」**，最后一页显示「已全部加载」；另外设计空结果、加载中、出错三种状态，以及排序或筛选变化时重置列表的过渡。
2. **深链接（US-12）**：深链接本身和登录回跳已经实现，**不需要重新设计流程**。只需要设计：「复制链接」入口；「找不到或无权访问」页（非成员访问返回 404，与「不存在」合并成一个页面，不区分两种情况）；「链接失效」页，用于无法识别的 page 段（见 O4）。角色不够的 403 沿用现有的无权限提示。
3. **写操作超时与重试反馈（US-13b）**：超时提示、重试按钮、「已成功，无需重复」的反馈。只有响应带 `Idempotency-Replayed: true` 时才显示这个反馈。
4. **项目级成员管理（US-14）**：成员列表、添加成员、**在本项目内停用**（二次确认文案必须写明「仅停用其在本项目的访问，并立即吊销其在本项目委托的 Agent 会话；不影响其在其他项目的成员身份；其已负责的任务不会自动转交」，**不能**写成「无法登录」或「登录会话失效」，因为本人仍然可以登录）、最后一个管理员不能停用时的错误提示。
5. **项目归档和恢复、仓库登记（US-15）**：归档确认（不要求输入项目名，见 O9）、归档被阻塞时列出阻塞项、已归档项目的「恢复」入口、仓库登记表单；需要空状态和错误状态。
6. （可选，低优先级）GitHub 同步失败的错误展示（US-5）：沿用现有错误组件即可，jack 只需确认文案和样式，不需要新设计。
7. **账号级停用界面（US-14b，【Weh 已确认 Q9+Q9a】本期要做，M5）**：组织级入口（仅**组织 ADMIN**可见/可点）、账号级停用二次确认（文案可写「停用后无法登录」）、与项目级停用入口严格区分；非组织 ADMIN（含仅有项目 ADMIN）看到禁用态或 403 提示。须配合**新增组织 ADMIN 角色**的展示（如何识别/授予不在本期 UI 细节外另开故事则在实现时最小可用）。

要求：沿用现有 HeroUI/Tailwind 体系；三种语言的文案长度要留有余量（尤其是 ru-RU）；通过 axe-core 可访问性检查。时间上，第 1–3 项在 M4 开工前交付，第 4、5、7 项在 M5 开工前交付。

### 14.1 对 jack 问题的回答（ui-spec-next-phase.md 第 472–480 行）
