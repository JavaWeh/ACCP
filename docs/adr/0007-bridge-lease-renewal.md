# ADR 0007：常驻 Bridge 的有界自动续租

## 状态

已实现，真实客户端再次联合验收待执行。本决策调整 M2 的客户端显式心跳责任，仅对常驻 stdio Bridge 生效，不修改 REST 协议、服务端租约或人工验收边界。

## 背景

[联合验收](../acceptance-2026-09-16.md) 发现模型主动心跳有 35、55、42 秒间隔，等待工具确认还发生过失租。仅依赖提示词无法在模型或人工等待期间保证续租。心跳会递增 Run version，因此简单增加定时器会使后续报告和成果提交持有旧版本，并破坏重试的请求摘要。

## 选择

- 常驻 stdio Bridge 为当前连接领取的 Run 管理后台心跳；当前每 20 秒调度，早于服务端建议的 30 秒，心跳请求超时 5 秒。单次 CLI 和通用 SDK 保持显式调度。
- 按 Run 串行化心跳和前台写入，只补偿自身后台心跳导致的版本推进。前台报告和显式心跳划定新的版本下限，错误 fence 不修正。
- 记录每次写入的参数摘要和首次实际请求头，重复请求仍交给控制面鉴权及幂等校验。每个 Run 限 4096 条记录，内存映射不持久化。
- 未知心跳结果用相同请求重试；未知前台写入暂停心跳并要求原参数重试。只在已知有效租约内续租，不根据猜测延长本地有效期，不自动领取新 Run。
- MCP ping 检查连接存活。断开、拒绝、终态、已知过期，或连续 30 分钟没有成功 Run 工具调用时停止。读取不能重启已停止的调度；自动续租不能证明模型仍在执行，也不能强制终止客户端进程。

## 替代方案

仅增强模型心跳提示不能覆盖人工等待；延长服务端租约会延迟孤立任务回收；让心跳不改变版本会改变既有并发和契约语义。单独创建无限续租守护进程容易失去与客户端连接的生命周期关联。

## 后果与重新评估条件

后台心跳会增加 API 和审计负载，串行 HTTP 请求仍可能受网络延迟影响，20 秒调度不是严格时序保证。30 分钟空闲上限需要长时间执行的客户端定期读取或报告 Run 状态。进程重启丢失请求头映射，必须通过服务端核对未知结果，不能换 key 盲目重做。

使用虚拟时间和竞态检测验证等待、重试、并发、空闲及停止条件；真实 PostgreSQL 和 MCP stdio 回归等待超过原 90 秒租约。真实厂商客户端、进程暂停和生产网络时序仍需分别验收。若试点需要更长无工具等待、跨重启恢复或更大并发，再评估可配置空闲策略、持久化操作账本与专用 Adapter 生命周期协议。
